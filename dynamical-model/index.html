Dynamical Model

For 4D analysis, observations yt∈RDy\vect{y}_t \in \mathbb{R}^{D_y}yt​∈RDy​ at times t=0,1,…,Tt = 0, 1, \ldots, Tt=0,1,…,T must be connected to the initial state x0∈RDx\vect{x}_0 \in \mathbb{R}^{D_x}x0​∈RDx​ through the rollout (1.3), where ftf_tft​ propagates the state forward from time 0 to time ttt. The dynamics enter the cost as the composition ht∘fth_t \circ f_tht​∘ft​.

vardax does not own dynamics; those come from somax (geophysical fluids), plumax (atmospheric transport and methane) or any user code. What vardax owns is the interface to dynamics (the pipekit_cycle.ForwardModel protocol) and the adjoint composition (delegated to diffrax.AbstractAdjoint).

The ForwardModel protocol¶

A forward supplies step(state, dt), a default dt and a state_signature. The Lorenz-63 model below, with state x=(x1,x2,x3)∈RDx\vect{x} = (x_1, x_2, x_3) \in \mathbb{R}^{D_x}x=(x1​,x2​,x3​)∈RDx​ standing for the (x,y,z)(x, y, z)(x,y,z) of (15.1) and the vector field f(t,x)f(t, \vect{x})f(t,x) of that equation (written with its arguments, to tell it from the rollout ftf_tft​), with the parameters σ\sigmaσ, ρ\rhoρ and β\betaβ of Lorenz-63, advances by forward Euler steps and satisfies the protocol structurally, and the check prints True; the later blocks on this page build on it.

somax.ShallowWaterModel, plumax.GaussianPlumeForward, and user-defined dynamics all satisfy this protocol natively. From vardax’s perspective they’re interchangeable.

For multi-step rollouts, vardax composes step calls into a trajectory with a lax.scan; a forward that is an ODE integrates each step with diffrax.diffeqsolve itself. The choice of ODE integrator (Tsit5, Dopri5, Heun, …) is on the dynamics, not on vardax.

Why the adjoint matters¶

The strong-constraint 4DVar cost (6.1) sums an observation term over every time. Minimising it over x0\vect{x}_0x0​ requires the gradient (6.2), which by the chain rule pulls each weighted residual Ht⊤Σε,t−1(ht(ft(x0))−yt)\mat{H}_t^\top \gmat{\Sigma}_{\varepsilon,t}^{-1} (h_t(f_t(\vect{x}_0)) - \vect{y}_t)Ht⊤​Σε,t−1​(ht​(ft​(x0​))−yt​) back to the initial time through Ft⊤\mat{F}_t^\topFt⊤​, where Ft∈RDx×Dx\mat{F}_t \in \mathbb{R}^{D_x \times D_x}Ft​∈RDx​×Dx​ and Ht∈RDy×Dx\mat{H}_t \in \mathbb{R}^{D_y \times D_x}Ht​∈RDy​×Dx​ are the tangent-linear dynamics and observation operator.

The transpose Ft⊤\mat{F}_t^\topFt⊤​ is the adjoint model, which was historically hand-coded line by line (Talagrand and Courtier 1987, Errico 1997). Modern numerical libraries make this far less painful: diffrax provides the adjoint of any diffeqsolve call automatically, in several flavours.

diffrax adjoint methods¶

vardax exposes forward_adjoint: diffrax.AbstractAdjoint as a constructor slot on StrongFourDVar, WeakFourDVar, IncrementalFourDVar and ReducedBasisFourDVar. It reaches diffrax through the forward: the model calls forward.with_adjoint(adjoint) (the SupportsForwardAdjoint protocol) and rolls out the forward it returns. A per-step forward has no integrator to hand the adjoint to, so passing forward_adjoint= with one raises ValueError; bound its memory with checkpoint= instead (below).

Default: RecursiveCheckpointAdjoint. Standard autodiff with recursive checkpointing, which balances memory and recompute. It supports reverse mode only, so as_forward_model(dt) differentiates each one-step solve with DirectAdjoint instead, which IncrementalFourDVar’s forward-mode tangent-linear model needs; pass as_forward_model(dt, adjoint=...) to choose another.

For long assimilation windows: BacksolveAdjoint. Solves the continuous adjoint ODE (12.1) backwards in time, with constant memory in the forward-trajectory length. Caveat: the reverse-time ODE may be stiff even when the forward ODE is not (diffusion-dominated problems, for example). If forward uses Tsit5, backward should typically use the same, and if the reverse problem is stiff, switch to an implicit solver; the diffrax docs list stable integrators.

For parameter estimation: ForwardMode. When you’re sensitive to a small number of parameters (e.g. a single emission rate QQQ in a methane Tier I problem), forward sensitivity is cheaper than reverse.

For debugging: DirectAdjoint. Plain reverse mode through the lax.scan of forward steps, slow but transparent. Its O(T)O(T)O(T) memory is fine for T=10T = 10T=10 steps but painful for T=1000T = 1000T=1000, so it is the wrong choice for long windows.

When the dynamics are linear¶

If ftf_tft​ is linear, the tangent-linear model (8.1) is just ftf_tft​ itself (no linearisation needed). For IncrementalFourDVar and operational 4DVar, the inner loop is in this situation: the outer nonlinear model is wrapped, but the inner loop operates on its tangent linear, computed once per outer iteration via jax.linearize and reused across many CG iterations.

The block below linearises one forward Euler step ΨΔt\Psi_{\Delta t}ΨΔt​ at μx=(1,1,1)\gvect{\mu}_x = (1, 1, 1)μx​=(1,1,1), pulls back a cotangent r∈RDx\vect{r} \in \mathbb{R}^{D_x}r∈RDx​ through its Jacobian F∈RDx×Dx\mat{F} \in \mathbb{R}^{D_x \times D_x}F∈RDx​×Dx​ and prints True.

For the unwrapped StrongFourDVar and WeakFourDVar, the full nonlinear ftf_tft​ is integrated each outer step and diffrax’s adjoint handles the gradient computation.

When the dynamics are stochastic¶

For SDEs (Langevin dynamics in Lagrangian transport, stochastic parameterisations), diffrax still applies: diffeqsolve handles SDE integration via EulerMaruyama, Heun, etc., and the adjoint methods work in the SDE setting too (with caveats around non-deterministic reverse integration).

vardax does not currently expose dedicated SDE-DA classes; the existing 4DVar variants work as long as the SDE realisations are seeded deterministically (e.g. via a jax.random.PRNGKey carried through the batch).

Forward model rollout in practice¶

For typical 4DVar with between T=10T = 10T=10 and T=100T = 100T=100 assimilation cycles and a shallow-water ForwardModel, the rollout (1.3) is one diffeqsolve saved at every step. Inside vardax, the rollout is composed inside the cost function. Per-step forwards: checkpoint=¶

Most forwards are a single step(x, dt) (an RK4 step of a finite-volume model, a learned emulator). Reverse mode through a lax.scan of such steps stores every intermediate of every step. The 4DVar models’ checkpoint= slot runs the rollout through integrix.adjoint.checkpointed_scan, which wraps blocks of steps in jax.checkpoint, so the backward pass recomputes them instead: True checkpoints every step, an integer k every block of k steps, with a shorter last block when k does not divide TTT. The gradient is unchanged.

On Lorenz-96 (Dx=40D_x = 40Dx​=40, RK4, T=500T = 500T=500 steps, float64, CPU) the compiled gradient’s temporary memory drops from 1.61 MB to 0.49 MB with checkpoint=True and to 0.37 MB with checkpoint=10. What remains is mostly the trajectory itself, which the observation cost reads at every time.

Performance considerations¶

  • Vectorise over the batch dimension, not the time dimension. Time is intrinsically sequential; batch is embarrassingly parallel. Use eqx.filter_vmap over the batch axis.

  • Checkpoint sparingly with RecursiveCheckpointAdjoint. The default number of checkpoints (int(log2(n_steps)) + 1) is usually right. Override only if profiling shows memory pressure.
