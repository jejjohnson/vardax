Problem Setting

Data assimilation is the problem of estimating the state of a dynamical system given partial, noisy observations and prior knowledge. It sits at the intersection of Bayesian inference, optimisation and numerical analysis; the prior comes from a physical model (or a learned one), the likelihood comes from instruments, and the posterior is what we want.

The Bayesian picture¶

Let x∈Rnx \in \mathbb{R}^nx∈Rn denote the state and y∈Rmy \in \mathbb{R}^my∈Rm the observations. Bayes’ theorem gives the posterior

p(x∣y)∝p(y∣x)p(x)p(x \mid y) \propto p(y \mid x) p(x)p(x∣y)∝p(y∣x)p(x)
(1.1)

which has three ingredients:

  • Prior p(x)p(x)p(x). What we know about the state before seeing the data. Most commonly it is Gaussian, x∼N(xb,B)x \sim \mathcal{N}(x_b, B)x∼N(xb​,B) ((4.1)), with background mean xbx_bxb​ and background-error covariance BBB. In FourDVarNet the prior is replaced by a learned autoencoder; in AmortizedPosterior it is absorbed into the trained head.

  • Likelihood p(y∣x)p(y \mid x)p(y∣x). How observations relate to the state. Chapter 2 models them as H(x)H(x)H(x) plus Gaussian noise with covariance RRR ((2.1)), so p(y∣x)=N(y;H(x),R)p(y \mid x) = \mathcal{N}(y; H(x), R)p(y∣x)=N(y;H(x),R), where the observation operator HHH maps state space to observation space.

  • Posterior p(x∣y)p(x \mid y)p(x∣y). What we infer about the state given the data. For a Gaussian prior and a Gaussian likelihood with linear HHH it is Gaussian in closed form ((4.3), chapter 4); otherwise we approximate it.

The maximum a posteriori (MAP) estimator minimises the negative log-posterior,

x∗=arg⁡min⁡x{−log⁡p(y∣x)−log⁡p(x)}x^* = \underset{x}{\arg\min} \left\{-\log p(y \mid x) - \log p(x)\right\}x∗=xargmin​{−logp(y∣x)−logp(x)}
(1.2)

and with the Gaussian prior and likelihood above the bracket is, up to a constant, the 3DVar cost (5.1) of chapter 5. When the state evolves through dynamics MtM_tMt​, we add a time index and a forward rollout, which gives 4DVar (chapters 6 to 8).

When dynamics enter: the 4D problem¶

Consider a state x0x_0x0​ at the start of an assimilation window and observations yty_tyt​ at times t=0,1,…,Tt = 0, 1, \ldots, Tt=0,1,…,T. A dynamical model MtM_tMt​ propagates x0x_0x0​ forward,

xt=Mt(x0)x_t = M_t(x_0)xt​=Mt​(x0​)
(1.3)

where xtx_txt​ is the state at time ttt.

The 4D variational cost adds an observation term for every time to the background term. In strong-constraint 4DVar (chapter 6) the dynamics are exact, the control variable is x0x_0x0​ alone and the cost is (6.1). In weak-constraint 4DVar (chapter 7) each step carries a model error ηt\eta_tηt​ with covariance QtQ_tQt​, the cost (7.2) gains a model-error term, and the control becomes the augmented vector (x0,η1,…,ηT)(x_0, \eta_1, \ldots, \eta_T)(x0​,η1​,…,ηT​).

In the linear-Gaussian limit (linear HtH_tHt​, linear MtM_tMt​, Gaussian BBB, RtR_tRt​, QtQ_tQt​) the posterior is Gaussian in closed form. In all other cases we minimise JJJ iteratively. The cost itself is the same; the solver is where the methods diverge.

The role of the forward model¶

The dynamics MtM_tMt​ and the observation operator HtH_tHt​ are the physics. vardax does not own them; somax (geophysics), plumax (atmospheric transport and methane) or any user code can supply them, as long as they satisfy pipekit_cycle.ForwardModel and pipekit_cycle.ObservationOperator respectively.

This means the same analysis class accepts any forward. A StrongFourDVar doesn’t know whether MtM_tMt​ is a shallow-water solver from somax, a Lagrangian particle simulator from plumax, or a neural emulator trained from physics outputs. The interface is fixed; the implementation is a slot.

This separation is what makes vardax composable with the broader JAX ecosystem (diffrax, optimistix, lineax, gaussx, pipekit-cycle) without bespoke per-method wiring.

Computational ingredients¶

The four computations that recur in every DA method:

  1. Forward model rollout (1.3). ODE integration via diffrax; vardax composes it but does not implement it.

  2. Tangent-linear and adjoint Mt′M'_tMt′​, Mt′⊤M'^\top_tMt′⊤​. Computed via diffrax.AbstractAdjoint (recursive checkpointing, continuous backsolve or forward sensitivity; see chapter 12).

  3. Observation operator Ht(xt)H_t(x_t)Ht​(xt​) and its tangent linear Ht′H'_tHt′​. See chapter 2 (linearize() contract via lineax).

  4. Inner minimisation arg⁡min⁡xJ(x)\arg\min_x J(x)argminx​J(x). Via optimistix.AbstractMinimiser (Gauss-Newton, BFGS, NonlinearCG, fixed-point iteration). For incremental 4DVar, arg⁡min⁡\arg\minargmin is done by CG on the linearised quadratic subproblem.

Each computation is owned by an upstream library. vardax composes them into DA algorithms; it does not reimplement them.

Posterior, not point estimate¶

A MAP x∗x^*x∗ is the start of the answer, not the end. Real DA produces a posterior (mean, covariance and provenance) that downstream consumers (population models, alert systems, decision pipelines) need.

vardax exposes a Posterior(mean, cov, samples, provenance) container returned by every analysis. Approximations include the Laplace (LaplaceCovariance) at MAP, the Gauss-Newton Hessian inversion (GaussNewtonHessian, free for IncrementalFourDVar), the ensemble covariance (EnsembleCovariance via filterax), or direct sampling from amortized heads. See chapter 13.

For the closed-form case (OptimalInterpolation) the posterior is exact, with the covariance (4.5) derived in chapter 4.

Reading order¶

Chapters 1 to 3 establish the shared foundation: this chapter (the problem), chapter 2 (the observation model) and chapter 3 (the dynamical model and its adjoint).

Chapters 4 to 10 cover one analysis method each, in the order of the table above, from OptimalInterpolation in chapter 4 to AmortizedPosterior in chapter 10, so in increasing order of sophistication.

Chapters 11 to 14 cover cross-cutting concerns: observation operators (the averaging-kernel and multi-instrument family), adjoint composition via optimistix and diffrax, posterior covariance, and the six-step research-to-operations methodology.

Chapters 15 to 17 are end-to-end examples on Lorenz, SSH and methane.

The companion design docs in design/ document the API contracts and architectural decisions behind these methods.
